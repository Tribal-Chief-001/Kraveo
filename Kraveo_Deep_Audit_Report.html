Kraveo Deep Audit Report

Implementation, security, platform, product and launch-readiness audit for the VIT Bhopal food-delivery platform

Prepared 6 August 2026 · Read-only audit · No source files changed

Executive verdict. Kraveo is a compelling and unusually thoughtful campus-delivery prototype, but it is not safe or functional as a live food-delivery marketplace. Do not accept real money, collect real GPS, or onboard external users until the critical launch blockers in this report are resolved and independently tested.

1. Executive scorecard

2. Audit method and verified checks

Three specialist audits covered backend/security, Flutter/mobile platform, and web/product/operations. The following checks were verified:

  • Backend TypeScript build passes; admin web production build passes.
  • Existing Flutter tests pass: customer 14, vendor 4, driver 3.
  • Current production Node dependency audits show no known vulnerabilities.
  • Flutter analysis reports 49 informational issues total: customer 28, vendor 17, driver 4.
  • There are no backend API tests, web tests, end-to-end tests, CI workflows, deployment infrastructure or Prisma migrations.
  • The running API uses in-memory stores; Prisma schema exists but Prisma is not instantiated or used.

4. Critical launch blockers

SeverityFinding and evidenceRequired directive
CriticalPrivilege escalation. backend/src/routes/api.ts accepts a role from unauthenticated login input; a caller can receive an ADMIN JWT.Use verified phone-OTP authentication. Public registration creates students only. Provision vendor, driver and admin roles through audited back-office workflows.
CriticalOrders and PII are exposed. Order list/detail routes do not require authentication and return customer, hostel, driver and drop-off data.Require authentication and central ownership policy on every query. Return role-specific, privacy-minimised DTOs.
CriticalAny authenticated role can update any order. Generic status mutation has no actor or resource check.Replace generic status updates with actor-bound commands: vendor accept/prepare, driver pickup/arrive, server OTP delivery confirmation.
CriticalPayment integrity is broken. Orders are marked PAID before verification; arbitrary amount/order input is trusted; live gateway errors become simulated success.Use payment-pending orders, integer paise, server-calculated amount, verified provider webhooks, idempotency, refunds and daily reconciliation.
CriticalCustomer checkout cannot finish. It awaits a non-dismissible dialog and subsequent completion code is unreachable.Replace with cancellable payment/loading state and test an end-to-end successful checkout path.
CriticalMobile apps are disconnected local demos. API config exists but no real HTTP, socket, auth or repository integration is present.Build typed API client, sessions, repository/state layer, sockets, retries, error states and durable local cache.
CriticalDelivery OTP is bypassable. Driver code accepts universal fallback codes and customer OTP is locally generated.Generate, hash, expire and verify OTP server-side for the assigned driver/order with rate-limit and attempt lockout.
CriticalSocket.IO is unauthenticated. Any origin can connect, join arbitrary rooms and emit global driver/order events.Authenticate handshakes, derive rooms server-side, remove client-authoritative events and publish privacy-safe role DTOs only.
CriticalRelease Android manifests have no INTERNET permission. Permission appears only in debug/profile manifests.Move required permission to main manifests and check merged release manifests in CI.
CriticalAll backend state is volatile. Runtime uses mutable arrays/maps.Implement PostgreSQL persistence, transactions, optimistic concurrency and transactional outbox before a pilot.

5. High-priority platform findings

Mobile and release

  • No push notification, app-killed alert, background job, map, GPS, navigation, payment SDK or offline synchronization implementation exists.
  • Vendor alarm depends on a remote audio URL; fallback only logs console text.
  • All Android apps use generic com.example.* IDs, generic branding and debug signing for release.
  • No iOS projects exist despite documentation presenting customer and driver iOS support.
  • Accessibility work is incomplete: no semantic labels, no TalkBack/font-scale test evidence and color-dependent status signals.

Admin and operations

  • Admin has no login, session expiry, MFA, role model, audit trail or staff approval workflow.
  • Status actions update UI optimistically but ignore rejected backend responses; vendor onboarding, toggle and driver reassignment are largely local-only.
  • The live map is visual only: driver latitude/longitude is not used for geographic positioning.
  • Analytics/KPIs are static data rather than defined operational metrics.
  • There is no observability stack: structured logs, traces, metrics, error reporting, alerting, backup restore test or incident runbook.

6. Documentation and governance

Documentation strength: the architecture, UX and rollout documents are comprehensive. However, the README and several documents present planned/simulated capabilities as currently operational. Introduce an IMPLEMENTED / SIMULATED / PLANNED capability matrix immediately.
  • Remove “production-ready” wording until launch gates are satisfied.
  • Add an OpenAPI reference, architecture decision records, threat model, data inventory, retention policy, support/refund/cancellation runbooks and incident/disaster-recovery plan.
  • Before launch, obtain appropriate professional review for vendor food-safety obligations, university/gate permission, privacy/data protection, consumer terms/refunds, runner safety/insurance, tax/settlement and payment compliance.

7. Recommended target architecture

Use a well-tested modular monolith first. Do not add microservices before the core order lifecycle is reliable.

LayerTarget responsibility
Flutter appsTyped authenticated client, encrypted session storage, durable local cache/outbox, role-specific UX and reliable error/reconnect states.
API backendIdentity, catalog, order, dispatch, payment, notification, admin/support modules with a central authorization policy.
PostgreSQLSource of truth for users, memberships, vendors, menus, orders, payments, payouts, OTP attempts and immutable audit/order events.
Redis and worker queueSocket adapter, cache, presence, delayed tasks, notification retries and dead-letter processing—not the source of truth.
IntegrationsVerified Razorpay webhooks, Firebase Admin/FCM, media object storage/CDN and maps/routing provider.
OperationsOpenTelemetry, error reporting, health/readiness, metrics, alerts, backups, reconciliation jobs and runbooks.

Core rules: integer paise for money; UUID/ULID identifiers; transactional commands; idempotency keys; immutable event/audit history; transactional outbox; authenticated server-authorized sockets; OpenAPI contracts; privacy-minimised response DTOs.

8. Required order lifecycle

Cart → Quote calculated → Payment pending → Payment verified → Vendor notified → Vendor accepted/rejected/timed out → Preparing → Ready for pickup → Driver offered → Driver assigned → Picked up → Arrived at gate → OTP verified → Delivered

At valid stages, separately model cancellation, payment failure, refunds, support disputes, driver reassignment, vendor timeout and safety incidents. Every command must record actor, timestamp, reason, policy check, idempotency key and audit event.

9. Execution roadmap

Phase 0 — Stop-the-line fixes: 1–2 weeks

  1. Remove tracked environment files from Git history and rotate every potentially exposed secret.
  2. Fix checkout and release network permissions.
  3. Delete universal OTP bypasses, demo progression controls, payment-success fallbacks and development-admin token fallback.
  4. Publish a truthful capability matrix and revise production-ready claims.
  5. Set up protected main branch, reviews, environment separation, secret handling and baseline CI.

Exit gate: no privilege escalation, no fake paid order path, clean release manifest, truthful documentation and automated build/analyze/test checks.

Phase 1 — Trusted commerce core: 3–6 weeks

  1. Implement PostgreSQL, Prisma migrations, repositories, transactions and seed data validation.
  2. Build phone OTP identity, server-managed roles and vendor operator memberships.
  3. Make server authoritative for catalog, quote, price, coupons, fees, order, delivery OTP and payment records.
  4. Implement verified Razorpay webhook lifecycle, refunds and reconciliation ledger.
  5. Add authorization tests, API integration tests, payment tests, migration tests, rate limiting, security headers and structured logs.

Exit gate: no cross-user access, all payment events reconcile, and restarts preserve all business data.

Phase 2 — Real fulfilment: 4–8 weeks

  1. Connect mobile apps to authenticated API and Socket.IO clients.
  2. Build FCM vendor alerts with bundled alarm assets, retry and acknowledgement behavior.
  3. Build driver availability, offer/accept/expiry, assignment locking, earnings ledger and delivery proof.
  4. Add consented location, map/routing, geofences, freshness detection and privacy retention controls.
  5. Convert admin into a role-based, server-authoritative, auditable operations console.

Exit gate: a real order can travel from customer through verified payment, vendor, driver and OTP delivery, including recoverable connectivity failure.

Phase 3 — Controlled campus pilot: 3–4 weeks

  1. Begin with one small service zone, limited hours, small vendor set and manual-dispatch fallback.
  2. Obtain campus/gate approval, vendor compliance evidence, packaging process, runner vetting and safety escalation plan.
  3. Establish cancellation/refund, support, food complaint, outage and rider incident runbooks.
  4. Use staging with test payments, push, maps, seed data, monitored dashboards and a verified backup restore drill.

Phase 4 — State-of-the-art optimisation

  • ETA and prep-time prediction; capacity-aware dispatch and batching.
  • Geofenced service zones, demand-aware delivery fees and vendor SLA management.
  • Runner utilization, safety-aware dispatch and fair earnings systems.
  • Personalization and experiments only after reliable fulfilment.
  • Operational analytics: fill rate, acceptance, prep SLA, dispatch lag, ETA error, delivery success, cancellation, refund, contribution margin and repeat rate.

10. Final directive

Do not spend the next month adding more screens. Preserve the excellent UX already built and focus on: persistent data, secure identity/ownership, verified payments, real mobile connectivity, reliable dispatch/location/notifications, and tested pilot operations. That is the path from convincing demo to defensible food-delivery business.
