# Kraveo pre-demo bug hunt - shared brief (6 Oct 2026)

You are one member of a bug-hunting team. A LIVE DEMO of Kraveo (campus food delivery for VIT Bhopal: customer app, restaurant partner app, delivery partner app, admin dashboard, Node backend) happens tomorrow in front of real people. Your job is to find every bug that could embarrass the demo, hurt a user, lose money, leak data or let an attacker in - in YOUR assigned scope - by reading the code line by line.

## 0. Rules (hard)
- READ-ONLY. Do not edit, create or delete anything in the repo. Write your report ONLY to the path your assignment gives (under /home/lucifer/Documents/Projects/Kraveo/Docs/bughunt/). Do not run git commit/push/checkout/stash. Do not run builds, Gradle, `flutter test`, `jest`, `npm test`, docker, dev servers, browsers, or ssh. (The laptop has 7.4 GB RAM and is shared. Reading files, `grep`, `git log/show/diff`, `wc`, and light `dart`/`node -e` snippets for pure logic are fine.) Never print secrets (.env, keys, tokens). Never contact production.
- Read EVERY file in your scope completely (not just greps). Also read the tests of your scope: tests that assert wrong behaviour or miss the dangerous cases are findings too. Budget your effort so you really cover the whole scope; if you cannot finish, say exactly which files you did not read.
- Evidence rule: a finding needs file:line, the exact trigger (concrete inputs / sequence of taps / requests / timing), what actually happens (trace the code, do not guess), and what the user/demo sees. Label each CONFIRMED (traced in code) or SUSPECTED (needs a device/browser/runtime). Do not pad: no style nits, no "could be refactored", no duplicates of the accepted limitations below.
- Rank by DEMO IMPACT: BLOCKER (demo stops or money/data/security breach), HIGH (visible failure in a normal demo path), MEDIUM (visible in a plausible side path or on small/odd devices), LOW (rare/cosmetic). Also give a FIX SIZE (S/M/L) and the minimal fix. Mark items that need the OWNER's decision or input (copy, business rule, credentials, external console) as OWNER-INPUT.

## 1. Personas - use ALL of them on your scope
1. BLACK-HAT ATTACKER (professional): authz bypass/IDOR/role confusion, token & session abuse, replay, race conditions (double submit, parallel requests), mass assignment, injection (SQL/NoSQL/HTML/URL/deep link/intent), SSRF, XSS (stored/reflected/in map popups/CSV), open redirects, brute force/rate-limit gaps, enumeration, secret leakage in logs/bundles/APKs, client-side trust (anything the app decides that the server must decide), business-logic abuse (free food, double refund, coupon reuse, cancel-after-pickup, fake location, fake delivery, OTP bypass), denial of service (huge bodies, unbounded lists, expensive queries, socket floods).
2. QA TESTER: every screen x every state (loading, empty, error, offline, partial data, very long text, Hindi/emoji, huge numbers, 0 and negative, special characters), every form field validation, every button double-tapped, back button / app switching / rotation / process death / resume, small phones (360x640), large font scale (1.3x-2x), dark mode if supported, slow network, timeouts, retries, clock/timezone differences, permissions denied.

UX/PRODUCT REVIEWER: dead ends, confusing copy, missing feedback, wrong or stale information on screen, flows that need too many taps, states where the user cannot tell what is happening or what to do next, unreadable contrast, tap targets too small, destructive actions without confirm, inconsistent wording between the 3 apps and the dashboard (status names, order numbers, amounts, drop point names).
4. CHAOS / SECOND-ORDER THINKER: for each important flow ask "what if X fails or arrives twice or late or out of order exactly while Y is happening?" Think about what the previous change could have broken elsewhere (regressions), and about state that lives in two places and can drift.
5. DEMO DIRECTOR: walk through the realistic demo script (customer places an order and pays by card/UPI test mode, restaurant gets the alarm and accepts, rider accepts, picks up, arrives, OTP, delivered, refund of a cancelled order, admin watches the live map and orders, a new restaurant signs up and is approved, rider goes on duty) and note anything that can go wrong on stage and how visible it would be.
