# Restaurant location: auto-detect by the restaurant + manual by admin (contract, 5 Oct 2026)

Owner decisions (settled): dual mode. (1) The restaurant sets its own pin from the Restaurant Partner app by auto-detecting with the phone's GPS: offered in the create-account form (next to "where is the kitchen") and, if still missing, asked again with a popup at every login/app start until it is set. (2) Admin can always set or correct any restaurant's pin by typing coordinates in the dashboard (already built: vendor drawer/manager and add-partner). If GPS fails the restaurant is NOT locked out: the popup can be dismissed ("Not now"), a banner stays until the pin exists, and admin can fix it from the dashboard. Everything must degrade gracefully and must not regress what works today.

Existing building blocks (Docs/19): `backend/src/config/campus.ts` (`checkVendorLocation`, `isNearCampus` within 3 km of the campus centre, `vendorHasLocation`, placeholder pin 23.0768/76.8524 = "not set"), admin `PATCH /api/admin/vendors/:id/location`, `OrderView.vendor.hasLocation`, dashboard CampusMap + vendor location input.

## 1. Backend (and the web dashboard)

- Additive migration (new folder, next free timestamp after `20261007_...`): `Vendor.locationSource String?` (`DEVICE` | `ADMIN`), `Vendor.locationSetAt DateTime?`, `Vendor.locationAccuracyM Float?`. No data rewrite. Admin location updates (existing endpoint and the create paths) set source `ADMIN`, setAt now, accuracy null.
- `POST /api/auth/partner-signup` for a vendor accepts optional `lat`, `lng`, `locationAccuracyM`. Rules: both lat and lng or neither; numbers (not strings); validated with `checkVendorLocation` (400 with `field` `location`/`lat`/`lng` and a plain message on failure); accuracy optional number 0..5000. Stored with source `DEVICE`. A signup WITHOUT a location still works exactly as today.
- `PUT /api/partner/vendor/location` body `{ lat, lng, accuracyM? }`: role VENDOR only, acts on the caller's OWN vendor row (never an id from the body), allowed while the application is PENDING, APPROVED, (REJECTED/SUSPENDED: 403 like other partner writes - follow the existing `requireApprovedPartner` conventions but PENDING must be allowed here; check how `/partner/application` does it), same validation, rate limited (10 per hour per user; add a rule next to the others in `middleware/rateLimit.ts`), audit-logged (`VENDOR_LOCATION_SET`, no coordinates needed in the text beyond rounded values), sets source `DEVICE`. Response: `{ success:true, data:{ lat, lng, hasLocation:true, locationSource, locationSetAt, locationAccuracyM } }`. A device update must not silently overwrite an `ADMIN` pin that is more than 3 km away - it is already limited to campus by validation, so no extra rule; but include `previous` coordinates in the audit text so admin can see a change.
- `GET /api/partner/me` (and the vendor object returned at login / `vendorView`) includes `hasLocation`, `lat`, `lng`, `locationSource`, `locationSetAt`, `locationAccuracyM`.
- Admin endpoints that list vendors / applications include the same location fields. Dashboard: (a) Applications panel shows the location a pending restaurant sent (coordinates, accuracy, a "Open in Google Maps" link, and a small "not provided" state) and lets the admin type/paste coordinates before approving; (b) vendor manager and drawer show a source badge ("Set by the restaurant on <date>, about 12 m" / "Set by admin" / "Not set"); (c) a restaurant without a real location appears in the needs-attention / health area with the text "No location - riders cannot navigate to it". Keep the existing dashboard tests and build green; add helper tests.
- Tests (jest): signup with/without/invalid/half location, near-campus rejection, string coordinates rejected, PUT happy path/validation/rate limit/role (customer and rider get 403, another vendor's id in the body is ignored), PENDING vendor allowed, REJECTED blocked as per conventions, `/partner/me` fields, audit row, admin edit sets source ADMIN, migration applied to the test DB (apply the SQL with docker exec and run prisma generate; verify `prisma migrate diff` is empty). Existing 571 tests must keep passing.

## 2. Restaurant Partner app (apps/vendor_app)

- New dependency `geolocator` (same major as the driver app) and Android permissions `ACCESS_FINE_LOCATION` + `ACCESS_COARSE_LOCATION` in the MAIN manifest (they were removed earlier because nothing used them; this feature is the reason; foreground one-time use only, NO background location, NO foreground service).
- A `LocationCapture` abstraction (fake in tests) that: explains why before the system prompt ("Riders use this to find your kitchen. We only read your location when you tap Detect."), handles denied / denied-forever (offer app settings) / GPS switched off (offer location settings) / timeout, and collects fixes for up to about 20 s keeping the MOST ACCURATE one; accepts when accuracy <= 40 m, otherwise shows the result with a clear "GPS is weak - step outside and try again" and a Retry button (the restaurant may still accept a weaker fix with a confirm). Shows the result before saving: coordinates, accuracy ("about 12 m"), and an "Open in Google Maps to check" link; two buttons: "Save location" / "Try again". If the detected point is not within 3 km of the campus, say so and do not save.
- Create-account form: under the existing address field add "Use my current location" (secondary button). On success show a chip "Location captured (about 12 m)" with "Change"; its values are sent with the signup (`lat`, `lng`, `locationAccuracyM`). The form still works without it (optional). If detection fails show the clean popup with the reason and options "Try again" / "Continue without" (the login popup below will ask again).
- After login / app start for a signed-in restaurant whose profile says `hasLocation == false` (also PENDING ones, on the application-status screen): show ONE modal bottom sheet per app start "Set your restaurant location" ("Riders cannot find you until this is done") with primary "Detect my location" and quiet "Not now", plus a persistent banner on the home / status screen until the location exists. Saving calls `PUT /api/partner/vendor/location`, then refreshes the profile; on failure (network, 4xx message) show the server message and keep the banner. An approved restaurant with a location sees an "Update restaurant location" row in its account/settings sheet (same capture flow, with a confirm because it changes where riders go).
- Do not break the existing push permission cards and banners (they must not stack into an unreadable pile: only one notice at a time as today, location notice has priority after push permission is settled - decide sensibly and document), the alarm, signup validation or any of the 194 existing tests (edit an existing test only where behaviour legitimately changes; list it).
- Tests with fakes: capture happy path, weak fix, retry, denied, denied-forever, GPS off, timeout, outside campus, signup payload with and without location, login prompt shown once per start and only when `hasLocation` is false, banner persistence, PUT success/failure handling, settings update confirm, no overflow at 360x640 / 1.3x text. Bilingual helper texts where the form already uses English + Hindi lines.

- Privacy page already mentions the restaurant's campus-map location; add one line that the restaurant's location is read from the phone only when the restaurant taps Detect.
